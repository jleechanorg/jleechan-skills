# Starter Kit iOS

Turn the product brief into a runnable app, not a plan. Start in a new directory or an empty target repo. Use an existing app as a **read-only architecture reference** only if the requester supplies it and access is available. Reuse the working patterns, not the codebase, brand, identifiers, credentials, users, assets, or release automation.

## 1. Define the product with user stories

- Write 3–5 prioritized user stories in the target repo: As [user], I want [action], so [outcome]. For each, record Given/When/Then criteria for visible state, navigation, persistence and recovery where relevant. Mark one end-to-end journey as the first runnable slice. Record the app name, repository and non-goals. If the brief is loose, choose reversible defaults and write them down. Reserve questions for decisions that block implementation or require authorization.
- Default to Expo + React Native + TypeScript + npm lockfile. For matching a supplied reference, read its package manifest/lockfile, Node pin, app config, native plugins, CI, and build profiles at a fixed revision. Pin a compatible SDK/React/RN/Node combination; do not copy the dependency list or use a new SDK template while claiming to match an older SDK. Without a reference, pick a currently supported Expo template and record the resolved versions.
- Keep a new app's display name, bundle ID, URL scheme, Expo project, app registration and auth client distinct. Default to isolated backend and auth environments; for a port, a shared API is acceptable only on an explicitly approved staging or development environment with dedicated users and isolated data. Set a unique dev identifier before native install. Don't link, register, or upload to an existing project as a shortcut. Choose one navigation system; keep data and service adapters outside screens.
- Start from the Expo template matching that decision ([Expo setup](https://docs.expo.dev/build/setup/)). Use `npx expo install` for Expo/native dependencies, commit package.json and its lockfile together, and prove a clean `npm ci`. Prefer config plugins over hand-edited generated projects. Never run clean prebuild when the native sources are uncommitted or maintained by hand.

## 2. Build the slice

- Sketch the first journey in a phone-sized mock, including its loading, empty, error and success states. Use it to make layout decisions before wiring the full flow. Build the shortest complete path with real controls. For a notes app: list → create/edit → save → relaunch → reopen the same note. Treat art, text hierarchy, safe areas, keyboard handling and accessibility as visible acceptance criteria.
- Choose the smallest stack beyond Expo: SQLite for structured offline data, key-value storage for small non-sensitive preferences, secure storage for auth tokens, and a typed API client only when sync or a service is needed. When actions stream, show partial output separately; commit one completed action by stable ID and never persist an interrupted response as success. Exercise one failure/retry path and one empty/loading state. Build the storage seam first; real API/auth comes through an adapter when approved and required.
- Provide a deterministic local mode from a clean clone so the slice works without accounts. Label fixture data, auth and provider output explicitly. For real auth, restore sessions across restart and test account isolation; use an approved isolated backend and dedicated test users. Do not send private data to a model. Provider keys, signing keys, and server secrets never go in JS bundles or `EXPO_PUBLIC_*`. Use backend-mediated provider calls.

## 3. Prove it, web first and native second

1. Run `npm ci`, `npx expo-doctor`, the project typecheck (e.g. `npm run typecheck`), and focused tests. Add the missing scripts/tests if the template has none. Test the expected resume behavior and at least one relevant failure or interruption; assert on the actual outcome, not just exit codes or UI prose.
2. Run the same Expo UI on phone-sized web where supported (`npx expo start --web`). Capture the clean baseline and the working path when a behavioral comparison exists. Label any fixture rather than presenting it as real service integration.
3. For native proof use an authorized macOS host with Xcode and an installed iOS Simulator runtime. Record `xcodebuild -version` and `xcrun simctl list devices available`, and select an isolated available simulator. Compile using the [Expo local iOS build flow](https://docs.expo.dev/guides/local-app-development/); for unattended testing use a supported headless build/install/launch route, not UI automation against a shared simulator. Verify the installed app and exact bundle ID, exercise the flow at least once and verify the story-specific outcome after relaunch. Reopen the saved item when persistence is part of that story. Capture a continuous recording in the supported orientation (portrait by default) plus a short receipt. Expo Go, web, JS export, a completed EAS build, an unlaunched artifact, and a green build workflow are not proof of running the installed app. If no authorized Mac/runtime is available, finish the other checks and say native verification is blocked.
4. Linux CI can run typecheck and tests; an iOS simulator or signed archive uses macOS. Inspect existing CI and EAS triggers before the first push; do not push if doing so would build, submit, or publish outside the task's approval. Do not enable publishing triggers in the starter. An EAS simulator profile is optional when already authorized. Device signing, store distribution, TestFlight upload and release are distinct steps: reuse only an authorized team-level signing process, never the reference app’s app registration or provisioning profile. Before a native build or upload, inspect the resolved bundle ID, URL scheme, EAS project ID if linked, and build/submit credentials and destination if configured; stop on any collision or unverified target. An upload requires the new app’s approved App Store Connect record. Stop for any required access or approval. See [EAS profiles](https://docs.expo.dev/build/eas-json/) and [submission](https://docs.expo.dev/submit/ios/). A queued build, archive, skipped CI job or successful workflow aggregate does not establish upload or App Store Connect processing.

## 4. Iterate to visual acceptance

- For each story, inspect the actual rendered UI at normal and large text, compact iPhone and (if in scope) larger sizes, and the applicable themes. Run the interaction, not just a static screenshot. Compare the behavior to its Given/When/Then and the screen to the mock; log what differs, fix it, and recapture at the new commit. Cover loading/error/success and keyboard or permission prompts where they change the journey.
- For a greenfield app, label the first runnable baseline or the mock honestly; do not fabricate a pre-existing app. Keep annotated screenshots or a continuous recording linked to story IDs and the exact commit, viewport, backend/fixture mode and observed result. Use an independent visual reviewer when available or required. Continue on concrete findings; when a human owns the design decision, present the actual before/after and keep visual acceptance pending until they approve. A story fails acceptance if its outcome fails, no matter how polished it looks. For a persistence story, include save → relaunch → reopen with the expected persisted result in the receipt. A screenshot, passing test, or draft PR is not visual approval.

## Agent handoff

Use the following input format, then implement without stopping at planning:

> Build **[app]** in **[empty target]**. Its first runnable journey is **[user action → visible outcome → evidence after relaunch, if relevant]**. Use **[optional authorized Expo reference/ref]** read-only. Start with a deterministic fixture and add **[approved service, or none]**. Deliver a clean checkout, startup commands, tests, and a native simulator receipt if a supported Mac is available. Do not upload or release.

Return the repo/ref, exact install and start commands, resolved toolchain, passing/failing checks, recording or explicit blocker, and what used real services versus fixtures. If publishing was requested, use the target repo's draft PR workflow. Put outstanding store/signing steps last and report only the stage actually verified.
