# Proxy Chain Provider-Masquerade Class (verified 2026-07-30)

## Symptom

User reports a runtime failure on a deployed URL like `consensus-ml.ai/?conversationId=…` with a browser-rendered error like:

```
Error: Cerebras API failed: Cerebras API error: 402
```

— but the failure is NOT actually a Cerebras-direct failure. The displayed provider name comes from the **UI label**, while the actual upstream the proxy hits is a different provider (in this case: OpenRouter). The proxy re-emits the upstream's raw error body to the browser unchanged, then the browser wraps it with the UI-side model label.

## Why this happens

Multi-model "consensus" apps typically route every model call through a single proxy (often OpenRouter or a custom aggregator) so that the frontend can talk to one HTTP endpoint and the proxy handles auth/credit accounting/rate limits per provider. From the frontend's perspective, the *model name* it sends (`cerebras-primary`, `gpt-4o-mini`, `gemini-2.0-flash-exp`) is just a label; the proxy decides which upstream provider to call based on that label. If the proxy's account has insufficient credits, every model returns `code:402` with the OpenRouter-shaped JSON body — and the frontend re-renders it as `<display-label> API failed: <display-label> API error: 402`.

## The diagnostic recipe (verified)

### Step 1 — Confirm the LLM call is server-side, not client-side

```bash
# Pull the SPA's main JS bundle and grep for fetch URLs to provider hostnames
curl -fsS https://<site>/assets/index-*.js | \
  grep -aoE '(fetch\([^)]{0,300}\))' | sort -u

# Also probe for the provider hostnames directly
for h in api.cerebras.ai openrouter.ai api.openai.com api.anthropic.com \
         generativelanguage.googleapis.com api.perplexity.ai api.groq.com; do
  echo "--- $h ---"
  curl -fsS https://<site>/assets/index-*.js | grep -aoE ".{40}$h.{80}" | head -2
done
```

If NO provider hostname appears inside any `fetch(...)` call, the LLM call is **server-side**. The frontend only sends a sturdier `Authorization: Bearer <firebase-id-token>` (or plain session cookie) to `https://<site>/<some-path>` and the proxy forwards to OpenRouter/Cerebras/etc. on the backend.

**Verified result on `consensus-ml.ai` (2026-07-30):** the SPA bundle contained only two fetch URLs — `/_log` (telemetry) and `/api/contact` (contact form). The `cerebras-primary` model string appeared only in **synchronous mock fixture code** (`ul=(e,t)=>({primary:{model:`cerebras-primary-${t}`,modelId:"cerebras-llama-3.3-70b",…}}`) — never inside a `fetch`. **The entire "Cerebras API error" trail was generated by the backend Cloud Run container.**

### Step 2 — Identify the backend Cloud Run service

```bash
# Find the production service serving the domain
nslookup -type=CNAME <site> 2>&1 | head
# consensus-ml.ai → 216.239.38.21 (Google SOA → likely Cloud Run via run.app URL map)

# Across all projects the user has gcloud access to:
for p in $(gcloud projects list --format="value(projectId)"); do
  for svc in $(gcloud run services list --project="$p" --platform=managed --format="value(name)" 2>/dev/null); do
    url=$(gcloud run services describe $svc --platform=managed --region=us-central1 --project="$p" --format="value(status.url)" 2>/dev/null)
    [ -n "$url" ] && echo "$p / $svc -> $url"
  done
done
```

**Verified result (2026-07-30):** `consensus-ml.ai` was served by `ai-universe-consulting-v2` in `worldarchitecture-ai` (revision `00012-86w`, image `gcr.io/worldarchitecture-ai/ai-universe-consulting:latest`). The revision logs showed clean startup + the express-style access log lines (`POST /v1/chat/completions 200 1700 - 33.949 ms`) but **no upstream stack traces** — the proxy just re-emits the upstream 402 to the browser.

### Step 3 — Probe the upstream directly to confirm the masquerade

```bash
# Send the same body shape the browser sends
curl -fsS -X POST https://<site>/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"<displayed-model-name>","messages":[{"role":"user","content":"hi"}],
       "stream":false,"max_tokens":8}'
```

If the body comes back with `"code":402` and `"limit_source":"openrouter_credits"` (or `remedy_hint: Add credit…`), the upstream is OpenRouter's billing wedge, not a real model failure. **The masquerade is confirmed.**

### Step 4 — Probe each candidate key against the *real* provider

```bash
# For each key the user provided, probe every model name the UI references
for k in <key1> <key2> <key3> <key4>; do
  for m in <model-from-UI> <model-2> <model-3>; do
    code=$(curl -sS -m 12 -o /tmp/r.json -w "%{http_code}" \
      https://api.cerebras.ai/v1/chat/completions \
      -H "Authorization: Bearer $k" \
      -H "Content-Type: application/json" \
      -d "{\"model\":\"$m\",\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}],\"max_tokens\":8}")
    body=$(head -c 200 /tmp/r.json)
    echo "$k -> $m http=$code body=$body"
  done
done
```

**Verified result (2026-07-30):** all 4 keys authenticated against Cerebras. The model name the UI displayed (`qwen-3-235b-a22b-instruct-2507`) returned `{"code":"model_not_found"}` 404 on **every key**. The actually-reachable models on every key were `gpt-oss-120b`, `gemma-4-31b`, `zai-glm-4.7`. **The keys were fine; the displayed model name was stale.**

### Step 5 — Confirm where the proxy reads its provider key

```bash
# Inspect the deployed service's env / secret refs
gcloud run services describe <svc> --platform=managed --region=us-central1 \
  --project=<project> --format=json | \
  python3 -c "import sys,json; d=json.load(sys.stdin); t=d.get('spec',{}).get('template',{}).get('spec',{}); \
  [print(c.get('name',''), '->', [(e.get('name'), e.get('value') or 'secret:'+(e.get('valueFrom',{}).get('secretKeyRef',{}) or {}).get('name')) for e in c.get('env',[])]) \
   for c in t.get('containers',[])]"

# Cross-reference stored OpenRouter secret fingerprint
for p in <project> <other-project>; do
  fp=$(gcloud secrets versions access latest --secret=openrouter-api-key --project=$p 2>/dev/null | \
       python3 -c "import sys; x=sys.stdin.read().strip(); print((x[:8]+'…'+x[-4:]) if x else 'EMPTY')")
  echo "$p openrouter: $fp"
done
```

**Verified result (2026-07-30):** `ai-universe-consulting-v2` and `ai-universe-2025 / ai-universe-dev` both reference `OPENROUTER_API_KEY` from Secret Manager (worldarchitecture-ai: `sk-or-v1…359d`, ai-universe-2025: `sk-or-v1…43eb`). The 402 came from those upstream accounts being out of credit.

## The two fix options

### Option A — Top up the OpenRouter account (operator-side, no code change)

Visit https://openrouter.ai/settings/credits and add credits to the account that owns the stored `sk-or-v1-…` key. This is the smallest, fastest fix and unblocks the UI immediately. The error wording `visit https://openrouter.ai/settings/credits` is OpenRouter's own hint — they pre-tell you the remedy.

### Option B — Repoint the proxy to direct Cerebras (requires code change)

Edit the deployed `ai-universe-consulting` image so it uses one of the working `csk-…` keys directly via `CEREBRAS_API_KEY` env var (or Secret Manager reference) instead of routing through OpenRouter. Update the model name in the request body from `qwen-3-235b-a22b-instruct-2507` to one of the actually-reachable models (`gpt-oss-120b`, `gemma-4-31b`, `zai-glm-4.7`). This is the durable fix — the proxy stops depending on a third-party aggregator's billing state. **Requires the repo that builds the image (likely `ai_universe_convo_mcp/scripts/setup-secrets.sh` or similar) to be edited and a new revision deployed.**

## Pitfalls

1. **Don't trust the user-facing error label for the actual upstream.** The proxy re-emits the upstream's raw error body; the browser wraps it with the UI-side model label. The label and the upstream can be different providers.

2. **Don't trust the displayed model name as a key probe target.** The proxy may accept a model name the keys don't actually allow. Always probe with `curl https://api.cerebras.ai/v1/chat/completions` (or the equivalent for the actual upstream) using the model name literally — the 404 vs 200 tells you whether the displayed model is even reachable.

3. **Don't bother probing key auth if the displayed model is the failing variable.** A 404 on `qwen-3-235b-a22b-instruct-2507` doesn't mean the key is dead — it means that model isn't available on that key. The key may be perfectly healthy for other models on the same provider.

4. **Don't assume the SPA is the LLM client.** Most "single-page-app" claim-checkers / aggregators fetch the LLM through a server-side proxy to keep keys off the wire. `grep -aoE 'fetch\([^)]{0,300}\)' <bundle>` is the fastest way to confirm.

5. **Don't stop at the Cloud Run revision logs when the failure is a 402-style "your account is out of credits."** The revision logs will show clean startup and `POST /v1/chat/completions 200 1700` style access lines; the proxy may emit the 402 to the browser with NO log line containing the upstream's error body. The error is *in the response body*, not the log stream. Reproduce the request with `curl` and inspect the body to see the actual upstream payload.
