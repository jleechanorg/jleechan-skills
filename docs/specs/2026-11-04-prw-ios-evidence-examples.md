# iOS workflow evidence examples

## Outcome
Make the iOS workflow guide's before/after evidence useful by showing obvious, real changes from merged frontend PRs: invitation artwork, response readability, portrait attachment and structured equipment.

## Non-goals
No app changes, new captures, generated screenshots, paper/Journal redesign, native claims for web captures, deployment or changes to the canonical workflow policy.

## Acceptance
Keep the approved invitation and readability examples. Add portrait and equipment pairs. Remove the open-PR Settings example. Every selected PR is merged; every image has an accessible original, verified hash, inspected pixels, source revision and explicit platform/scope limits. Preserve the older zoom and native iPad examples.

## User story
A developer reading the guide can compare the affected surface before and after, see why screenshots add information beyond tests, and distinguish the demonstrated improvement from untested behavior.

## Proof plan
Read live PR merge state and source provenance. Download and decode the original images, compare published hashes, inspect visible differences and record unmatched content or scale. Review the complete document diff independently, check links and mechanical structure, and run the applicable current-head review/readiness gates. Historical captures remain bound to their original revisions; documented source applicability is not a new run.

## Mock exemption
No mock is needed: the deliverable is a case-study document embedding existing real screenshots. Do not replace them with newly generated or retouched images.

## Risk
The main risks are exaggerated native/runtime claims, stale provenance, misleading comparisons and personal-account URLs in a portable repository. Label mobile-web evidence, retain limitations and original hashes, use project-owned evidence links, and keep merge authorization separate from review results.
