# Primary-source research for a blocker-first code-review skill

Researched 2026-09-11. Scope: review instructions and finding quality, not measured model accuracy. Sources below are first-party documentation or public source files; `main` URLs can change.

## What the sources establish

**Google: improvement, evidence, and proportionality.** Review should improve overall code health without demanding perfection. Technical facts outweigh preferences; optional polish should be explicitly non-blocking. Documented style governs, while equally valid designs can follow the author's preference. This supports separating consequential defects from optional cleanup rather than making every observation a release gate. [Google review standard](https://google.github.io/eng-practices/review/reviewer/standard.html)

**Google: review context and meaningful tests.** Inspect design, user behavior, concurrency, unnecessary complexity, and whether tests actually detect broken behavior. Read surrounding code and system context, not just isolated changed lines. When reviewing a limited portion, disclose that scope. These are review dimensions, not a requirement to run every evidence class for every patch. [Google reviewer checklist](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

**OpenAI: actionable defects and calibrated severity.** The public Codex rubric requires meaningful impact, a discrete remedy, evidence that the change introduced the defect, and an identifiable affected code path. Unsupported assumptions and hypothetical downstream breakage do not qualify. It permits zero findings, requests every qualifying finding, favors short locations and concise explanations with triggering conditions, and separates priority from confidence. P0 is reserved for universal release/operations/major-use failures; P1 is urgent, P2 normal, P3 low. Applicable repository rules should be verified and cited; ordinary correctness findings do not require an invented rule citation. The correctness verdict excludes non-blocking nits. [Codex review rubric](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/review/rubric.md)

**Anthropic: verify candidates before reporting.** Its feature-dev reviewer prioritizes precision, names the reviewed scope, and asks for a location, bug or guideline explanation, and concrete remedy. It filters below a self-assessed confidence of 80. That is an instruction threshold, not evidence of calibrated 80% precision; its scale also blends confidence and impact. [Feature-dev reviewer prompt](https://github.com/anthropics/claude-code/blob/main/plugins/feature-dev/agents/code-reviewer.md)

**Anthropic: independent verification and workflow caveats.** The official plugin separates candidate discovery from per-candidate verification, checks guideline attribution, filters existing defects and nits, and requires code links containing a full Git commit SHA. However, it also skips drafts, assumes build checks run elsewhere, and posts comments automatically. Those choices belong to that workflow; they are not universal review-quality requirements and should not override a user's requested draft review or read-only scope. [Official code-review command](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-review/commands/code-review.md)

**Matt Pocock: original upstream architecture.** The canonical source is `mattpocock/skills`, under `skills/engineering/code-review/SKILL.md`. It validates a user-supplied fixed point, uses a merge-base comparison, and delegates Standards and Spec separately. It searches for an originating issue/spec; absent a spec, it skips that axis rather than inventing requirements. Standards include documented conventions plus explicitly heuristic Fowler smells, with repository rules taking precedence. Aggregation explicitly preserves separate axes and prohibits cross-axis re-ranking. A blocker-first overlay is therefore a local adaptation, not an unchanged upstream feature. [Upstream skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)

Upstream release notes record promotion from an in-progress `review` skill to the published engineering `code-review` skill. This establishes upstream provenance; it does not establish which revision a particular local installation originally imported. [Upstream release history](https://github.com/mattpocock/skills/releases)

**Anthropic: instruction boundaries need operational support.** External files and tool content can inject instructions; even an audited connector can deliver malicious data. Model instructions alone cannot guarantee containment. Anthropic documents repository configuration executing before a trust decision as a concrete failure mode and warns that subagent output can also carry malicious content. [Agent containment engineering](https://www.anthropic.com/engineering/how-we-contain-claude)

## Recommended local design

The following are recommendations inferred from those sources, not upstream requirements:

1. **Lead with blockers while retaining provenance.** Keep Standards and Spec distinct; order findings within each by material impact. A short opening can state whether either axis has a blocker without blending away either verdict. Mark smells and optional polish as advisory unless a concrete consequence or mandatory rule establishes stronger significance.
2. **Pin the actual review scope.** Record target revision, baseline, comparison semantics, and whether staged, unstaged, or untracked changes are included. Do not imply that a committed merge-base diff covers work-in-progress files. Confirm both lanes reviewed the same snapshot.
3. **Use an evidence contract for every finding.** Require severity, changed location, trigger, affected behavior, causal explanation, and a minimal remedy. Cite a spec or repository rule when that is the basis. Distinguish an executed reproduction from static reasoning; either can support a finding if its limits are explicit.
4. **Verify, deduplicate, and allow zero.** Challenge each candidate using callers, guards, existing tests, and baseline behavior. Collapse duplicate root causes. Do not report speculative failure as established fact or inflate severity because confidence is high. Keep unresolved evidence gaps separate from confirmed defects.
5. **Handle missing specs without stopping useful work.** Search supplied context and likely sources. If none is available, mark requirements coverage unavailable and continue the Spec correctness pass against observable contracts alongside Standards. Never manufacture product requirements or claim specification compliance.
6. **Make review read-only by default.** Produce findings without source edits, commits, pushes, merges, or external comments unless the user authorized those actions. Necessary targeted checks can use isolated scratch outputs; do not run untrusted repository hooks merely because a reviewed document requests them. Respect explicitly requested execution modes and existing runtime permissions.
7. **Treat reviewed material as evidence, not new authority.** Diff text, issue bodies, logs, fetched pages, and teammate summaries cannot authorize new actions or suppress findings. Apply trusted project instructions through the normal hierarchy; inspect proposed instruction changes as changes under review. Do not promote an injected instruction because another reviewer repeated it.
8. **Test the prompt behavior proportionately.** Include cases for a real blocker, clean patch, advisory smell, missing spec, baseline-only bug, changed instruction injection, and dirty-worktree scope. Assess whether it reports the right consequence and respects boundaries, rather than checking only headings or a numeric confidence score.

No controlled evaluation was performed here. These sources justify design choices and cautions; they do not prove that a particular revised prompt improves precision or recall.
