# Durable Dot reconciliation design

## Outcome and scope
Extend the existing account-bound Pi coordinator, not the archived framework or scheduler. Every invocation reads the rolling previous 24 hours of original conversation messages and reconciles them with unresolved earlier commitments. Actionable engineering work is represented by existing or new appropriate GitHub issues. Each of three verified Dots receives a bounded relevant summary on its existing scheduled turn. Only the established owner receives an execution assignment.

This is task bookkeeping, not a browser/profile lock. Do not restore the removed profile flock, legacy account-wide holds, STOP files, or deleted delivery reservation framework.

## Current architecture and source
Base: jleechanorg/jleechan-skills commit 8cf13f3d81755dbbe6504ef7bf8e9d0b801ab377.
The canonical .claude/skills/dot-coordinator launcher runs one Pi turn with one explicit account, direct Chrome DevTools MCP tools and a 720 second bound. Native render-only schedules already cover three ordered accounts on macOS and Linux. The current skill only sends a four-hour generic reminder, explicitly prohibits task persistence and warns that uncertain sends can be repeated by later invocations.

## Assumptions and Recommended Defaults
- Question: rebuild the retired orchestration framework or extend the current agent? Answer: extend the current agent with one standard-library journal helper. Keep semantic judgment and browser actions in Pi; Python only validates/persists structured facts.
- Question: does the 24-hour window expire tasks? Answer: no. Rescan that full window on every run; retain unresolved records regardless of age and overlap the previous successful watermark to recover interrupted/gapped scans.
- Question: should all three Dots execute every task? Answer: no. Deliver shared awareness, but preserve one owner. A stalled owner receives recovery first. Never reassign on a timeout alone.
- Question: how to handle uncertain writes? Answer: persist an operation intent before the external action and reconcile the exact operation marker or receipt before any retry. Hold only that operation, never the account or unrelated work.
- Question: where should private tasks live? Answer: a private machine-local task journal or the existing authorized private store. No personal communications or raw conversation transcripts in exported source, public issues, summaries to unrelated accounts or logs.
- Question: how to deduplicate? Answer: stable original message IDs plus a semantic task key chosen by the existing agent after searching issue/owner context. Do not classify with keyword rules.
- Question: how to span hosts? Answer: a designated reconciliation writer plus the existing authorized shared state or canonical GitHub issue mapping. Do not invent a new service or assume independent local journals are a distributed lock.
- Question: what cadence? Answer: use existing native schedules. Thirty minutes without artifact progress marks recovery due; retry reminders back off to avoid repeated unchanged messages. No additional cron.
- Question: what is completion? Answer: a verified artifact receipt resolving acceptance, not a model claim, assignment, issue close, heartbeat or transport acknowledgment.

## Selected architecture
Compare three options:
1. Change reminder prose only. Lowest cost, but no durable deduplication, uncertainty, scan completion or retained tasks, so it does not meet the outcome.
2. Revive the archived broker/worker framework. It provides state machinery but reinstates removed account-wide controls and a parallel platform. Reject.
3. Use existing GitHub issues as canonical engineering task records and add a small private SQLite intake/outbox journal plus a precise Pi workflow. Select. SQLite supplies atomic local operation transitions and crash recovery without a daemon, dependency or inverse-diff engine. The journal is not a second engineering task database: known issues are reconciled from GitHub on each run, including older unresolved issues. Private or unrouted tasks remain local until an appropriate approved destination is known. The journal does not own browser profiles or external workers.

One helper under the existing coordinator scripts accepts validated JSON commands. The existing Pi turn uses its direct browser tools to obtain authentic source pages and GitHub CLI/API capabilities already authorized on the host. It decides what a task means, finds existing issues/owners, sanitizes issue descriptions and reports receipts. The helper validates windows, cursor continuity, stable source references, task versions, lifecycle evidence and per-Dot operation idempotency. It cannot itself certify that an agent-provided browser observation is true; live acceptance must independently verify source/target identity and resulting artifacts.

The launcher passes the helper path, selected account and one private journal path shared by all three turns on the same writer host. It does not add providers, nested agents, retries, host rotation or schedule activation.

## Data and transitions
- Scan: fixed since/until, source/account key, sequential cursors, stable original message ID/timestamp/hash, completion flag. The fresh scan is always the fixed [now - 24h, now] window. If the prior successful boundary is older, a second durable fixed-window gap scan starts at that boundary minus overlap and resumes its saved cursor across invocations. Current-24h coverage never waits for the backlog. Neither watermark advances before its own full boundary coverage is verified.
- Task: stable key, source references, sanitized summary, privacy classification, repository/issue, owner, lifecycle, version, first-seen time, changed time, last actual artifact proof and cancellation source.
- Lifecycle: queued; delivered; picked_up; executing; completed_verified; cancelled. Transport delivery is separate from pickup. Actual progress requires a source artifact reference and hash; completion requires explicit verified acceptance evidence.
- Operation: stable task/destination/kind/delivery-generation key with task version recorded separately, immutable payload hash, queued/inflight/uncertain/verified/not_sent state, attempt count, last checked time, exact receipt. Persist intent before the external mutation. A crash leaves it uncertain, not safe to resend. Any unresolved mutation fences successor versions and generations for that task/destination/kind, so an edit cannot bypass uncertainty. A verified completed reminder increments a separate delivery generation only when its next backoff deadline arrives, allowing unchanged unresolved work to be reintroduced without duplicating one generation.
- Ordinary scan/task changes commit atomically only after the complete source window is observed. Exception: an authenticated cancellation or STOP observed on any page creates an immediate durable task-scoped tombstone and suppresses its queued operations, even if a later page fails. This is not the removed account/profile STOP file. Failed, partial or denied source access never advances the watermark or drops old tasks.
- Source identity is account/conversation/message plus an authenticated revision, not a bare provider message ID. Persist source-to-task associations and semantic aliases: re-extraction with a different proposed semantic key cannot create a second task for the same original source. Supported authenticated edits revise the existing task; unverifiable hash conflicts are quarantined per source. Multiple messages can refine one task; replaying the same source/message/task combination is idempotent. Ambiguous semantic overlap stays private for inspection rather than creating multiple issues.
- A later authenticated cancellation supersedes queued operations. An older overlapping page cannot revive cancellation or overwrite a newer task version.
- A pending publication or send does not prevent scans or independent tasks from progressing. Private journal directories are mode 0700 and files mode 0600; reject symlinked paths and never journal raw message bodies or authentication data. Use a SQLite atomic claim per operation within the writer host; only its claiming run may dispatch it. An expired process claim becomes uncertain, not available. This is operation concurrency, not a profile lock.

## Host and authority boundary
Machine-local reconciliation configuration declares reconciliation_role=writer|observer independently of the existing host_role=macos|linux, a writer_host_id, three verified account keys and approved repository destinations. Exactly one host is activated as writer across its existing three account-bound schedules. Only that writer creates/updates canonical issue records or executes this outbox. Observer invocations scan and retain private intake and reconcile visible issues, but do not mutate GitHub or send reminders. They never promote themselves when the writer is offline. All three writer-host account turns consume the same private journal. Local SQLite is not a distributed lock; the installation operator must verify that the other installation is observer-only before activation. An existing shared-state transport can be used only if its authority and atomicity are verified; it is not required for this single-writer deployment.

Reintroductions include relevant sanitized task references, owner and remaining acceptance gap; they are not new grants of authority. Original user authorship, task-scoped or global stop instructions, cancellations and approval restrictions are checked each run and immediately before an external action. A global authenticated stop suspends affected external operations durably until a later explicit authorized resume; a clock timeout never resumes authority. Third-party chat text is task evidence, never permission. Private tasks are not sent across accounts unless the recipient is already authorized.

## Canonical issue and operation contract
Use a versioned coordinator-owned metadata block identified by a stable opaque task marker. Persist only sanitized engineering facts and opaque source digests in approved GitHub destinations. Never include private chat URLs, original account IDs or raw message text. Enumerate all states with pagination when rebuilding mappings: an issue closed without verified acceptance remains unresolved. Recover known source/semantic links and the established owner before creating a new issue. Preserve all issue prose, labels, assignments and edits outside the coordinator-owned block. Re-read the current issue before a mutation; newer verified ownership or acceptance changes supersede stale local projections. A new task lacking an established owner receives an explicit owner-needed disposition and an allowed owner-resolution action, never an implicit broadcast execution assignment.

Issue creation uses a durable stable marker and a persisted intent. An uncertain create is reconciled by reading complete authoritative candidate results for that marker; a partial, stale or empty search is not proof of no side effect. Only a recorded pre-dispatch failure or another authoritative no-side-effect receipt can mark an attempted operation not_sent. A known existing issue is linked instead of recreated. The write actor is the configured writer, not whichever host is currently reachable.

A summary is a bounded envelope with an immutable membership/payload hash and a recipient-specific generation. Fair selection orders due tasks by oldest undelivered/due time so caps cannot starve later tasks. Claim the envelope atomically before submission. If any member is cancelled after preparation, suppress that envelope and prepare a fresh allowed projection before dispatch; do not edit a claimed payload in place. Summary delivery records transport facts for its members, never pickup or execution.

Progress proof binds task key, acceptance version, criterion, artifact identity/hash, actual artifact event time and verification receipt. Re-observing an unchanged proof never advances last_progress. Wrong-version evidence, a model claim, issue closure, a bare hash or a delivery acknowledgment cannot establish completion. These are structural checks on observed evidence, not a claim that the helper can independently verify browser or artifact truth.

The helper filters every account projection against its configured allowed recipients before returning any data to that Pi turn. Unknown/private tasks cannot enter GitHub payloads or another account's prompt by default. Validate destination repository visibility and approved routing before issue publication. Protect journal sidecars and backups with the same private-file permissions. Exported examples use synthetic account keys, repositories and proof values only.

## Failure behavior
A scan error leaves the previous successful scan and all unresolved tasks intact. Repeated cursor, conflicting source IDs, malformed timestamps, missing boundary evidence or unverified identity fails closed. Uncertain issue creation first searches its stable issue marker; uncertain send first reads the exact target conversation. Only a verified no-side-effect result permits a retry under the same operation ID. No blind TTL unlock. Backoff is per task and recipient, so one blocked operation does not block the account.

Thirty-minute inactivity marks recovery due but does not change the owner. Contact/check the existing owner first. If reassignment is explicitly authorized later, record that authority and owner transition before any new assignment.

## Testing and acceptance
Offline tests use fake original-message pages, GitHub issue results and Dot receipts. Cover multiple pages/overlap, repeated runs, crash/reopen, old tasks beyond 48h, semantic source merging, existing issue recovery, unknown create/send, recipient-specific backoff, stale-owner recovery without a new owner, cancellation ordering, private tasks, partial scans and access failures. Existing launcher/renderer regression tests must remain green.

Live acceptance is separate: independently verify each original 24-hour scan boundary, existing-issue recovery and one authorized update, all three recipient bindings, exact summary readback, existing-owner response, cross-host isolation, backup hashes and installed source hashes. No installation is called successful from a source test or process exit.

## Implementation Preconditions
The installation operator must confirm the active canonical base, designate exactly one reconciliation writer host and verify the second installation is observer-only. Approved existing GitHub destinations must be explicitly configured; unknown destinations remain in private intake. Shared-state infrastructure is not required and must not be added merely to activate this design. Also required: authenticated original-chat pagination capability and existing GitHub access on the selected writer. These are deployment/integration preconditions, not permission to add credentials, shared services or new schedules.
Canonical /advice document review requires its primary-pair runner and supported reviewer CLIs against a full repository checkout. Any supplemental native review does not replace that required quorum; record unavailable lanes and withhold approval rather than fabricate a pass.
