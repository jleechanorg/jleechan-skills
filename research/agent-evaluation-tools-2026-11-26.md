# OSS for reproducible agent and instruction evaluations

Research date: 2026-11-26. Scope: reusable foundations for a generic `/experiment` and `/experiment-skill` workflow, with a control replay before any treatment. This is a docs/repo review, not an execution or compatibility test.

## Recommendation

Implementation usage: [Harbor skill experiments](../docs/harbor-skill-experiments.md).

**Pilot Harbor as an execution substrate with a thin experiment adapter/manifest.** Harbor's task directory and trial model are a close match for repeatable agent work in a container: task prompt, task configuration, environment, verifier, optional reference solution, selectable agent/model, parallel trials, trajectories, reward, token/cost and duration reporting. It supports arbitrary agent integrations, so the skill experiment need not be represented as a code patch if its test task can package the actual prompt/config variation.

Keep the adapter responsible for experiment semantics Harbor does not promise: discover and pin the incident-era repository commit; capture the before/treatment instruction files and hashes; pin runtime, model identifier/settings and dependencies; require a successful control replay before treatment; run the same paired task set; retain run metadata and results; and optionally blind output review. Do not build a new general-purpose runner unless Harbor proves unable to invoke the target agent or preserve the necessary historical config.

**Harbor identity correction:** the official repository is [`harbor-framework/harbor`](https://github.com/harbor-framework/harbor), while the project website uses `harborframework.com`. The requested `harborframework/harbor` spelling is not the current official GitHub identity. The repository's latest release visible on the research date is v0.25.0 (released 2026-10-25); confirm/pin the exact release or commit at implementation time, since `main` and these docs are mutable. [Harbor releases](https://github.com/harbor-framework/harbor/releases)

## Verified capabilities and limits

- **Task/environment and verifier contracts:** Harbor tasks separate the instruction from the environment build context and verifier. `task.toml` carries resources and timeouts; `tests/test.sh` writes a reward file. The verifier may run in the same or a separate environment; use separate mode when tests/answer keys should not be visible to the agent. This gives a practical baseline gate: validate packaging/verifier with a known-good Oracle/reference solution when one is available, then run the actual control agent and require that the complaint-level behavior is reproduced before treatment. A passing oracle alone does not prove the control reproduces the complaint. [Harbor create-task guide](https://github.com/harbor-framework/harbor/blob/main/skills/create-task/SKILL.md)
- **Repository snapshots:** SWE-bench v5 makes its task tree and task-specific build context explicit and evaluates with Docker. For a skill experiment, use the affected repository's evidenced state before the failed action as the base checkout; store full SHA, repository URL, clean/dirty status, submodule SHAs and relevant LFS/artifact identifiers. If the historical state had uncommitted edits or ignored files, Git SHA alone is insufficient: preserve a patch or content-addressed snapshot. Pin the test/verifier commit separately if it is not part of that repository snapshot. [SWE-bench README](https://github.com/swe-bench/SWE-bench/blob/main/README.md), [SWE-bench v5 changelog](https://github.com/swe-bench/SWE-bench/blob/main/CHANGELOG.md)
- **Trajectory, token, time:** Harbor trial views report trajectory, token usage, cost, and phase timings. SWE-agent stores full query/action/observation turns and config; Inspect records model usage and total/working time; promptfoo persists output/result rows. Compare task success and regressions first, then tokens/cost and wall/working time. Capture each framework/agent adapter version because logging and usage accounting vary across versions. [Harbor example trial record](https://hub.harborframework.com/jobs/3de0aee9-6de7-4d94-83c4-ac5e789fe757/trials/f32e32b1-b6aa-4fad-a2b8-11b1ccaf2c5d), [SWE-agent trajectory schema](https://github.com/SWE-agent/SWE-agent/blob/main/docs/usage/trajectories.md), [Inspect log API](https://inspect.aisi.org.uk/reference/inspect_ai.log.html)
- **Repeated and paired runs:** Harbor's `--n-attempts` repeats each task; Inspect has `--epochs` with a reducer; SWE-agent batch supports fixed shuffled instance sets and parallel workers; promptfoo supports `--repeat N` and stable range/sample selection. These facilities give repeated observations, not automatic paired-statistical analysis. Keep the same ordered task IDs and environment across control/treatment, label each pair/seed, randomize execution order if drift matters, preserve every trial (including errors), then compute per-task paired deltas and uncertainty outside the runner. [Harbor evaluation guide](https://github.com/harbor-framework/docs/blob/main/guides/running-evaluations.mdx), [Inspect eval reference](https://inspect.aisi.org.uk/reference/inspect_eval.html), [SWE-agent batch runner](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/run/run_batch.py), [promptfoo CLI](https://github.com/promptfoo/promptfoo/blob/main/site/docs/usage/command-line.md)
- **Blinding:** None of the examined tools provides a complete blind-review protocol for comparing instruction conditions. Keep treatment labels out of graders/review packets where possible; export anonymized outputs in shuffled order and have an independent rubric grader score them. For objectively testable work, prefer deterministic hidden checks to model grading. LLM graders themselves need pinned judge model, rubric and run configuration, and their judgments should be retained with rationale for audit. Inspect and promptfoo have model graders, which is a capability rather than blinding. [Inspect scorers](https://inspect.aisi.org.uk/scorers.html), [promptfoo grader](https://www.promptfoo.dev/docs/red-team/troubleshooting/grading-results/)
- **Isolation:** Harbor task execution is designed around isolated environments and supports Docker and remote providers; SWE-bench uses Docker. Inspect provides sandbox providers. For arbitrary code, separate the verifier, deny unnecessary network egress, pin container images by digest, set CPU/memory/time limits, and avoid sharing mutable workspaces between trials. promptfoo's JavaScript safe mode is expressly not a sandbox. [Harbor README](https://github.com/harbor-framework/harbor), [SWE-bench README](https://github.com/swe-bench/SWE-bench/blob/main/README.md), [Inspect sandboxing](https://inspect.aisi.org.uk/tools.html#sandboxing), [promptfoo CLI](https://github.com/promptfoo/promptfoo/blob/main/site/docs/usage/command-line.md)

## Suggested incident-replay contract

1. **Define the replay point.** Resolve and record the incident/complaint timestamp, the evidenced repository full SHA before the failed action, and exact historical instruction/skill/runtime artifacts when available. Mark unknown fields explicitly; do not reconstruct or imply historical fidelity from a current checkout.
2. **Make a portable Harbor task fixture.** The task's environment checks out the SHA; its instruction is the captured control prompt; tests encode the complained-about behavior and independent regressions; verifier is isolated. Validate the verifier with a reference/oracle when available, then run control agent trials. Abort treatment if the package fails or actual control fails to reproduce the reported symptom.
3. **Run a paired treatment.** Change only the named instruction/skill under test. Keep model/provider/deployment/flags/tool versions, task IDs, seed data, verifier, resource limits and concurrency fixed. Use a small pilot to expose setup mistakes, then a predeclared number of repetitions on the same task set.
4. **Retain a complete run bundle.** Include task and verifier hashes, repo SHA, image digests, framework/agent versions, prompt/skill hashes, model ID/settings, per-trial IDs/seeds, raw trajectories/logs, token/cost/time data, scores, failures and run commands. Ensure API keys/secrets are excluded.
5. **Decide against a baseline gate and paired results.** Require baseline reproduction before treatment; report task-level pass/fail and regressions, paired deltas, repeat variability, cost and time. Blind any subjective grading; retain judge rubric/model and anonymized grading records.

`/experiment-skill` should be a thin specialization that locates the skill/instruction candidates and stages the before/after variants for `/experiment`. Keep project-specific task construction opt-in/local, and don't bake one product or repository into exported generic skills.

## Source versions and uncertainty

- Harbor identity and release: `harbor-framework/harbor`; v0.25.0 released 2026-10-25 according to the repository's release list. Its current main branch may have advanced since then; use a release or immutable commit for a real experiment. [Releases](https://github.com/harbor-framework/harbor/releases)
- SWE-bench: the current official changelog records v5.0.0 and v5.0.1 on 2026-08-17; v5 moves tasks into a versioned task repository with per-instance metadata and build context. [Changelog](https://github.com/SWE-bench/SWE-bench/blob/main/CHANGELOG.md)
- Inspect AI: current official pull request listing showed release PR `0.3.293` opened 2026-11-23, pending in that listing. Treat this as the inspected source state, not a verified installed stable package version. [Official PR listing](https://github.com/UKGovernmentBEIS/inspect_ai/pulls)
- SWE-agent and promptfoo: examined current official `main` docs and code; this review did not verify a precise latest release/tag. Pin immutable versions before a run. Promptfoo's release page showed v0.126.0 dated 2026-11-18 during research, but does not guarantee what is installed locally. [Promptfoo releases](https://github.com/promptfoo/promptfoo/releases)
- No source reviewed claims automatic reconstruction of historical agent instructions, prompt context, runtime dependencies, provider/model behavior, or uncommitted repository state. The experiment owner must supply these records. Reproducibility remains bounded by provider model updates and hosted API nondeterminism even with a fully pinned local fixture.
